Purpose and scope

For an ordinary non-bit tag, Read_U32.vi reads one unsigned 32-bit integer at a zero-based byte offset in an existing tag's local data buffer. The call reads local data; it does not itself request new data from the controller. Use Read_Tag.vi first when fresh tag data is needed, subject to the configured read cache.

The bundled binaries contain the version string 2.7.2. Native behavior below is based on upstream 2.0.22 unless a newer version is identified. The bundled binaries may behave differently. Version strings alone do not prove exact binary build provenance.

Called function and library selection

The Call Library Function Node calls:

uint32_t plc_tag_get_uint32(int32_t id, int offset);

The node uses the C calling convention and runs in the LabVIEW user interface (UI) thread. Its numeric arguments are passed by value.

Choose_Lib.vi receives the incoming error and supplies the path and its error output to the library node. The configured cases select plctag32.dll, plctag64.dll or libplctag64.so under the application directory. The default target case returns an empty path. The library arguments are the tag handle and byte offset. The node's return is the typed value.

Inputs

All connected terminals are marked recommended, rather than required. Wire the values needed for a predictable call.

For an ordinary non-bit tag, the offset counts bytes, not array elements. If the data buffer has size N, valid offsets satisfy 0 <= offset <= N - 4, provided N is at least 4. Use Tag_Size.vi to obtain the buffer size and check the size result. Validate the offset before the call; the older library uses an addition-based bounds expression that can overflow for extreme I32 values.

Outputs and error handling

OutputTypeMeaning
tag handle outI32Passes the handle through the library node. It is not proof that the operation succeeded.
tag valueU32The value returned by the C getter. It is data, not a separate status code.
error outError clusterLabVIEW call and incoming-error information. It is separate from the library return value.

The legacy getter returns UINT32_MAX (4294967295) if the handle is absent, the tag has no data buffer, or the requested range is out of bounds. The same numeric value can also be legitimate tag data, so the returned value alone cannot distinguish these cases. The legacy getter does not set tag status in these paths. Validate the handle, buffer size and preceding read before using the result; do not treat a later tag-status result as proof that this getter succeeded.

error out is the LabVIEW error cluster from the Call Library Function Node. An incoming true error status skips the call. A clear LabVIEW error cluster alone does not prove that the native getter found valid tag data.

Execution and C implementation

The node calls plc_tag_get_uint32 with the handle and byte offset. The legacy C function looks up the tag, takes its internal mutex and checks for a data buffer and space for 4 bytes. On the normal path it decodes the local bytes into a U32 value and returns that value to tag value. The legacy source uses the byte at the lowest offset as the least significant byte.

The getter releases its temporary tag reference before returning. It does not destroy the caller's tag. The call itself makes no request to refresh controller data.

Example and recommended call sequence

For a ready tag with at least 4 bytes, call Read_Tag.vi when fresh data is needed and check the read result. Use offset 0 to interpret the first 4 bytes as a U32 value. Ensure the tag layout actually contains that type at that location. Check error out and the native getter limitations before relying on tag value.

For example, assume a ready tag has local bytes 0x01 0x00 0x00 0x00 starting at offset 0. The legacy getter returns 1 if the handle and range are valid.

When finished with the tag, release it with Destroy_Tag.vi. Ensure cleanup can run even when an earlier operation has failed.

Library version differences

In the checked upstream 2.7.2 source, an integer getter on a bit tag reads its configured bit as 0 or 1 and ignores the byte offset. For an ordinary tag, byte order follows the tag settings. The library updates tag status on the checked data and range paths, but the VI still returns data rather than a separate native status. Validate the handle and range before relying on the value.
